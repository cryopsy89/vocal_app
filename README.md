## 0. Что это за проект (в двух абзацах)

Локальное macOS-приложение, которое объективно оценивает, насколько точно
пользователь попал в ноты, когда поёт короткий фрагмент песни под свой минус.

Главный вопрос, на который приложение обязано честно ответить:

> «Насколько хорошо я попал в мелодию, когда пою под конкретный минус?»

Результат вида: **«Ты попал на 84%. Вот конкретные места, где ты был ниже/выше и насколько.»**
Это НЕ Melodyne, НЕ автотюн, НЕ pitch visualizer. Пользователь не музыкант с идеальным
слухом — он не должен интерпретировать графики, ему нужна цифра + список проблемных мест.

Полный бриф — в инструкции проекта (project instructions). Здесь — только реализация Phase 1.

## 1. Общая архитектура (для контекста, реализуется не вся сразу)

Пайплайн разбит не по файлам, а по **осям неопределённости** — ошибки копятся на стыках:

```
                    ┌─ TARGET (что петь) ──────────────┐
original_song ─────►│ separation → f0 → note segments  │
                    └──────────────┬───────────────────┘
                                   │ (ноты в оригинальной тональности/темпе)
                                   ▼
              ┌──── TRANSPOSE (сдвиг по высоте) ────┐   chroma cross-correlation
              └──────────────┬──────────────────────┘   (ручной ввод имеет приоритет)
                             ▼
              ┌──── ALIGN (сдвиг по времени) ───────┐   DTW по мелодическому контуру
              └──────────────┬──────────────────────┘   (после транспозиции!)
                             ▼
        my_vocal ──► f0 ──► USER MELODY ──► COMPARE ──► score + confidence
```

Ключевые архитектурные решения (зафиксированы, не пересматривать без причины):

- **Главный риск проекта — не accuracy-формула, а цепочка извлечения target melody**
  (`full song → separation → f0 → notes`). Ошибки множатся. Поэтому Phase 1 работает
  НЕ на реальном аудио, а на синтетике с известной ground truth.
- **Transpose и align — ортогональны, решаются раздельно и в этом порядке:** сначала
  убираем сдвиг по высоте, потом по времени. Иначе align по мелодии сломается (контуры
  не совпадут по высоте).
- **Разные pitch-трекеры для разных входов:** pYIN для чистого пользовательского вокала
  (даёт честный voiced-флаг), CREPE для грязного извлечённого оригинала (устойчивее к шуму).
- **Transpose:** chroma cross-correlation, НЕ global key estimation. Даёт сдвиг по модулю
  октавы (0–11), направление неоднозначно → ручной ввод имеет приоритет над Auto.
- **Align:** DTW по контуру полутонов после транспозиции, с Sakoe-Chiba band. Начальная
  задержка вокала съедается первым шагом варп-пути — не плодит ошибки.
- **Confidence gating — first-class.** Показать кривой процент хуже, чем не показать ничего.

Фазы: **P1** — формула на синтетике (сделано) → **P2** — реальный pitch tracking (pYIN) →
**P3** — separation + transpose + align → **P4** — UI (Streamlit) → **P5** — training/retry mode.

## 3. Контракт формулы (самое важное — это спецификация compare.py)

### 3.1. Философия: одна цифра врёт

«Попал в ноты» распадается на две ОРТОГОНАЛЬНЫЕ оси, их нельзя схлопывать в один процент:

1. **Intonation** — когда пел, насколько точно по высоте (в центах).
2. **Coverage** — пел ли вообще нужную ноту в нужный момент, или молчал/попал не туда.

Можно спеть 100% чисто, но половину нот проглотить (intonation высокий, coverage низкий).
Считаем раздельно. Главная цифра — `p50`, но coverage и confidence ВСЕГДА рядом.

### 3.2. Уровень расчёта: по фреймам, не по нотам

Канонический расчёт — **frame-weighted** (фрейм ≈ 10 мс). Note-level — вторичная агрегация
фреймов для UI, НЕ основа score. Причины:
- note-level даёт короткой и длинной ноте равный вес — неправильно;
- длительность учитывается АВТОМАТИЧЕСКИ: длинная нота = больше фреймов = больше вес.
  Отдельного множителя длительности НЕ нужно.

### 3.3. Вход compare.analyze()

Транспоз и align считаются УЖЕ отработавшими. На вход `compare` приходят f0, которые
уже приведены по высоте и выровнены по времени, фрейм в фрейм:

```
f0_user     : np.ndarray  — Гц по фреймам, NaN = unvoiced
f0_target   : np.ndarray  — Гц по фреймам, NaN = unvoiced (СТАБИЛИЗИРОВАННЫЕ ноты, не сырой f0)
conf_user   : np.ndarray  — 0..1 уверенность трекера (Phase 1: единицы)
conf_target : np.ndarray  — 0..1
note_bounds : list[(start_frame, end_frame, note_name)] — границы target-нот
c_align, c_transpose : float — уверенность этих стадий (Phase 1: 1.0, ещё не подключены)
```

### 3.4. Пошаговая формула

**Шаг 1. Ошибка в центах (знаковая):**
```
error_cents(i) = 1200 · log2( f0_user(i) / f0_target(i) )
```
Минус = ниже цели, плюс = выше. Всё в центах (слух логарифмичен). NaN протекает сам.

**Шаг 2. Маски — что НЕ участвует в intonation:**
- `unvoiced target` — петь нечего, исключить.
- `unvoiced user, но voiced target` — молчал где нота. НЕ ошибка интонации (нет f0), но
  идёт в coverage как пропуск. Критично не путать: кинуть в intonation нельзя (нет значения),
  проигнорить полностью нельзя (можно смолчать весь фрагмент и получить 100%).
- `transition zones` — ±`transition_ms` вокруг границ нот (легитимное портаменто/атака), исключить.
- `vibrato frames` — фреймы нот с вибрато, исключить (иначе размах вибрато капает в ошибку).
- `low pitch-confidence` — НЕ выкидываем, а понижаем вес (может быть октавный срыв трекера).

**Шаг 3. Веса:** `w(i) = conf_user(i) · conf_target(i)`. По длительности отдельного веса нет —
встроен в frame-level (см. 3.2).

**Шаг 4. Целевое значение ноты** (тут живёт вибрато/мелизмы):
- `f0_target` — это СТАБИЛИЗИРОВАННАЯ нота, не сырой f0. Внутри сегмента высота одна.
- стабильный сегмент → медиана (устойчива к атаке); вибрато → центр = среднее по периодам,
  размах уходит в отдельную vibrato-метрику; короче `note_min_ms` → украшение, помечается
  transition и исключается.
- ⚠️ Граница «нота vs украшение» — НЕ математика, а калибруемый порог. Не прячем магию,
  выносим наружу (`note_min_ms`, `vibrato_min_extent_cents`).

**Шаг 5. Octave errors:** НЕ сворачиваем по модулю октавы (C4 ≠ C5). Но если |error| ≈ 1200
(±`octave_tol_cents`) → флаг OCTAVE. НЕ исключаем из score (реальная ошибка), но показываем
флаг: половина «октав» — срыв трекера, не пользователя. Решение — глазами/ухом, не автоматом.

**Шаг 6. Метрики:**
```
p25/p50/p100 = Σ w·[|error| ≤ T] / Σ w        # доля ВРЕМЕНИ внутри допуска
bias         = weighted_median(error)          # знаковая систематика
coverage     = voiced(user)∧voiced(target) / voiced(target)
note-level   : на ноту median(error); correct если |med| ≤ note_correct_cents И покрытие ≥ note_coverage_min
LOW/HIGH     : знак med у некорректных нот
worst        : top-N по |med|·√dur (длинные грязные ноты всплывают выше коротких)
```
Почему пороги, а не `100% − mean/что-то`: среднее нелинейно связано с восприятием.
10 нот по −20c звучат чисто, 1 нота −200c слышна, среднее почти одинаковое. Пороговая
доля ближе к уху: «сколько времени было приемлемо».

**Шаг 7. Confidence gate:**
```
C = min(C_coverage, C_tracker, C_align, C_transpose)   # MIN, не среднее!
if C < gate  →  LOW CONFIDENCE, числа скрыты
```
`min`, потому что слабое звено рвёт цепь: если align уехал, то p50=90% сравнил тебя не с тем
куском — среднее бы это замаскировало.

### 3.5. Выход (Result) — концепт UI

```
PITCH ACCURACY
within ±50c:  84%        ← ГЛАВНАЯ (доля времени)
within ±25c:  63%
within ±100c: 95%
coverage:     92%        ← спел почти всё нужное
bias:         −18c       ← чуть стабильно низишь
notes:        14 / 17 correct   (LOW 4  HIGH 2  octave-flagged 0)
worst:  01:37.8 D4 −71c | 01:43.1 F4 −83c | 01:40.2 A4 +58c
confidence:   OK
```

Result ТАКЖЕ возвращает пофреймовый ряд (`error_per_frame`, `score_mask_per_frame`,
`octave_mask_per_frame`) — он нужен deviation plot в Phase 4. Добавлен в контракт СЕЙЧАС,
чтобы потом не менять сигнатуру.

### 3.6. Решение по UI (зафиксировано)

- Главная цифра — **p50**, крупно. coverage + confidence рядом обязательно.
- **НЕ рисовать** две наложенные pitch-кривые (плохой UX из брифа).
- **Deviation plot**: одна кривая отклонения от цели, ноль = попал идеально, зелёный
  коридор ±50. Строится из `error_per_frame` — тот же источник, что p50, не могут разойтись.
  Роль: ЛОКАЛИЗАЦИЯ проблемы, не оценка (оценка — цифры).
- Дорожка нот блоками под осью X, цвет = вердикт, клик по красному → вход в training mode.
  Одно связывает диагностику и навигацию.
- Честность графика: unvoiced = разрыв (не ноль!); missed = серый блок; low-confidence =
  пунктир; octave = клип к краю + значок «октава?».

## 4. Описание файлов

### config.py
Один `@dataclass(frozen=True) Config`, инстанс `CFG`. Все числа, влияющие на результат — здесь.
Текущие значения (Phase 1, разумные «на глаз», НЕ откалиброваны на реальном вокале):

```
frame_ms = 10.0
thr_tight/main/loose = 25 / 50 / 100      # центы, пороги p25/p50/p100
transition_ms = 45.0                       # ⚠ калибруемый; в P2+ привязать к темпу
note_min_ms = 90.0                         # короче — украшение
note_coverage_min = 0.60                   # доля длительности, чтобы нота «покрыта»
vibrato_rate_hz = (4.0, 8.0)
vibrato_min_extent_cents = 20.0
octave_tol_cents = 50.0
gate = 0.5                                  # ниже → LOW CONFIDENCE
coverage_min_for_score = 0.30
note_correct_cents = 50.0
worst_top_n = 5
```

### synth.py
Генератор f0-контуров (Гц по фреймам, NaN = unvoiced). Работаем сразу в f0, не в waveform —
Phase 1 проверяет СРАВНЕНИЕ, не трекинг. Функции:
- `note_to_hz(name)` — 'C4'→261.63, поддержка #/b. C4 = MIDI 60, A4 = 440.
- `cents_to_ratio(cents)` — центы → множитель частоты.
- `steady(note, dur_s, offset_cents=0)` — ровная нота, опц. смещённая.
- `silence(dur_s)` — NaN (unvoiced).
- `vibrato(note, dur_s, rate_hz, extent_cents)` — синус вокруг центра ноты.
- `portamento(from, to, dur_s)` — плавный переход в лог-области.
- `concat(*parts)` — склейка блоков.
- `_n_frames(dur_s)` — внутренний, число фреймов по frame_ms.

### compare.py
Реализует контракт из раздела 3. Маленькие функции, каждая делает одно:
- `error_cents`, `voiced` — элементарные.
- `transition_mask`, `vibrato_mask`, `score_mask` — маски.
- `_weighted_fraction`, `_weighted_median` — агрегаты (с EPS, см. раздел 5).
- `coverage`, `octave_flags` — оси.
- `note_results` → `list[NoteResult]` — note-level для UI.
- `confidence` — gate (min компонент).
- `analyze(...) -> Result` — сборка всего.

### test_phase1.py
`_bounds(*segs)` — хелпер строит note_bounds. Каждый тест: строим target, строим user
ЗАВЕДОМЫМ смещением, проверяем что analyze вернул заложенное. Есть `__main__` для запуска
без pytest (печатает ok/FAIL построчно, exit code 1 при провале).

Покрытие (маппинг на Cases из брифа):

## 5. Найденный баг (важно, показывает зачем синтетика)

Case 3 (−100 центов) сначала **упал**. Причина: `1200·log2(...)` вернул −100.0000000001
(floating point), и условие `err_abs <= 100.0` его выкинуло → p100 стало 0 вместо 1.

Это РЕАЛЬНЫЙ баг формулы, не теста: любая нота ровно на пороге дёргалась бы «попал/мимо»
от шума в 14-м знаке. На реальном вокале выстрелило бы постоянно.

Фикс (в compare.py): допуск `EPS = 1e-6` центов в пороговых сравнениях —
`_weighted_fraction` (`<= thr + EPS`) и вердикт ноты (`<= note_correct_cents + 1e-6`).
Семантика: «ровно на пороге = попадание». 1e-6 центов на порядки меньше слышимого,
но гасит fp-дрожь. Тест НЕ ослаблялся — чинилась причина.

После фикса: **10/10**.

## 6. Границы Phase 1 (что СЕЙЧАС заглушено — честно)

Не баги, а честные границы фазы. Ни одна заглушка не притворяется рабочей:
- `vibrato_mask` определяет вибрато по разбросу внутри сегмента — временная логика.
  Настоящая сегментация вибрато/мелизмов уедет в `notes.py` (Phase 2).
- `c_align` и `c_transpose` в `confidence` зашиты в 1.0 — эти стадии не подключены.
  Стоят единицами явно, не притворяются, что что-то посчитали.
- Пороги в config.py НЕ откалиброваны на реальном вокале — только «на глаз».
- Вход `compare` — идеальные f0. Реальные (с octave slips, кривой voiced-детекцией,
  шумом на атаках) придут в Phase 2 и наверняка вскроют новое.

## 7. Точка входа в Phase 2

Phase 1 проверяла сравнение на идеальных числах. Phase 2 = реальный pitch tracking:

1. `pitch.py` — pYIN (через librosa) на чистом пользовательском вокале. pYIN даёт
   voiced-вероятность из коробки → прямо кормит confidence.
2. Прогнать pYIN на СИНТЕТИЧЕСКОМ wav (сгенерить waveform из известного f0), проверить
   что трекер возвращает тот же f0 → тогда доверяем связке «wav → f0 → compare».
3. Что вскроется и надо будет решать: octave slips трекера, voiced/unvoiced пороги,
   шум на атаках/согласных (Case 14), поведение на краях диапазона.
4. ПЕРЕД этим — отложенная проверка актуального состояния pitch-библиотек и separation-моделей
   (Demucs и альтернативы) на Apple Silicon: лицензии, MPS-поддержка, свежие релизы.
   Не зафиксировано, чтобы не советовать вчерашний день.

Стек (целевой): Python 3.11+, Apple Silicon/MPS, librosa, crepe/torchcrepe, Demucs (pending),
numpy, scipy, Streamlit (UI), sounddevice (запись). Всё локально, без облака/аккаунтов.

## 8. Инварианты, которые нельзя сломать (чек-лист для «другого меня»)

- Всё внутреннее — центы и фреймы. Секунды только на выходе для UI.
- Intonation и coverage — раздельно. Не схлопывать в один процент.
- Расчёт frame-weighted. Note-level — только агрегация для UI.
- Октаву не сворачивать (C4≠C5), но флажить.
- Unvoiced user при voiced target → coverage, НЕ intonation.
- Confidence = min компонент. Не среднее.
- Пороговые сравнения — с EPS (иначе fp-баг из раздела 5 вернётся).
- Все калибруемые числа — в config.py, не по коду. Никаких магических констант в логике.
- Никаких заглушек, которые выглядят рабочими. Не уверен → LOW CONFIDENCE / NotImplementedError.
